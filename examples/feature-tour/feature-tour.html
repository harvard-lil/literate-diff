Promote, do not rebuild

What changed

  • The suite runs against the bytes that ship. CI used to build one image to test and the deploy built another from the same source; now it builds one, tests the test stage on top of it, and the deploy ships the image that passed.
  • A deploy is a tag, not a build, so it takes seconds rather than minutes and cannot produce something the suite has not seen.
  • No AWS keys in the workflow. The job assumes a role through GitHub's OIDC provider, and the trust policy names one environment rather than every branch in the repository.

What to take from this

If you are setting up a deploy elsewhere. Promotion needs no service: the registry stores an image by digest, so shipping a tested image means adding a tag to a digest that is already there ↓. Two registry settings make it safe -- immutable tags, and a lifecycle policy that expires deployed images more slowly than candidates. Drop the habit of copying a settings module in at build time; choose it at runtime and the second Dockerfile goes away ↓.

If you review our AWS configuration. A deploy role whose trust policy names a branch can be assumed from any pushed branch. Name the environment instead S1.

The story

Before this change, every deploy built a fresh image on the prod branch and pushed it as latest, with production settings copied into the image at build time and long-lived AWS keys in the workflow. The suite never ran against the bytes that shipped.

After it, CI builds one image per commit, tests the test stage that is built from prod, and publishes it tagged with the commit. The deploy resolves that tag to a digest and ships the digest. The registry refuses to move a commit tag, keeps deployed images longer than candidates, and the deploy role trusts one GitHub environment rather than every branch.

… Not hard, and no service is needed. Promotion is a tag, not a copy: … the registry already stores the image by digest, so "promote" means adding a second tag to a digest that is already there.

The work is in the two things that make that safe. Tags have to be immutable, or a commit tag can be moved under you between test and deploy. And the lifecycle policy has to expire deployed images more slowly than candidates, or the thing you want to roll back to is collected before you need it.
